For most of the time I've been programming, my coding standard was pretty simple: make it work. If I could still understand it later, even better. If something wasn't obvious at a glance, I'd throw in a comment. Past that, I didn't think much about spacing, indentation, or how I declared a variable. The computer never complained.

Then ESLint showed up.

After working in Python, C, C++, Arduino, and CircuitPython, I was used to a decent amount of freedom in how I wrote things. Every language has rules, obviously, but I mostly focused on getting from problem to working solution. During my first week using TypeScript with ESLint, it felt like getting the program to run was only half the assignment. Then ESLint would show up with a list of everything it didn't like.

My first reaction was pretty much: this is annoying.

## Why Do You Care About My Spaces?

My first run-ins with ESLint weren't dramatic. Mostly it was spacing and indentation. My program ran fine, and I'd still get a red squiggly line telling me something was wrong.

At first that felt like rules for the sake of rules. If two versions of the code run exactly the same way, why does it matter where I put a space?

I still think linting can get overly picky, and I'm not totally sure where that line is. But the more I used it, the more I realized those small rules usually aren't written for the computer at all. They're written for whoever reads the code next.

A computer doesn't care if my code is ugly. My teammates do.

## When Annoying Becomes Useful

Not all of it was cosmetic, though. ESLint caught an unused variable once, and another time it flagged a variable I'd accidentally reassigned. Those weren't just style opinions. They were real problems in my code.

`const` vs. `let` in TypeScript tripped me up early on. My instinct was to just pick whichever worked and keep moving. Having the standard enforced made me actually think about what I was telling the program.

If a value is never supposed to change, why am I declaring it as something that can?

That's when I started to see how coding standards can double as a way to learn a language. ESLint doesn't just say "this is wrong." Sometimes it makes me ask why the language wants it written a certain way in the first place.

I still groan at a wall of ESLint errors. But there's a difference between annoying and useless, and I'm slowly realizing a lot of these warnings can be annoying and useful at the same time.

## Code Is Not Always Written Alone

Honestly, the biggest reason I've come around on coding standards is robotics, not ESLint.

When I write code alone, I know my own logic. I know why a file lives where it does, why I named something the way I did, and what I was thinking in some weird section. Work with other people on the same codebase, and that advantage is just gone.

I've opened teammates' code before and wanted to close the laptop. Not because it was bad. Sometimes it worked fine. The problem was that their logic didn't match mine, and I had to reverse-engineer how they thought before I could even figure out what the code did.

On a robotics team, you can't let everyone structure things however they want. We have to agree on where launch files go, how commands get triggered, and how the pieces talk to each other. Skip that, and every new person's code turns into its own puzzle to solve.

Standards can't make two people think alike, and I don't think they're supposed to. What they do is cut out the differences that don't need to exist. If we're both following the same conventions, I spend less time asking "why did you write it like this?" and more time asking what the code actually does.

## More Than Making Code Pretty

Before this, I thought of coding standards as basically formatting rules. I don't think that anymore.

Consistent spacing helps readability, sure, but rules around naming, unused variables, and project structure actually touch the quality of the software itself. They also mean that more than one person can look at the same code and land on roughly the same understanding of it.

That matters more as a project grows. Code only I can read is fine for something I'll never open again. It's a problem when someone else has to maintain it six months later, or when that someone else is future me, who's forgotten everything about why I wrote it that way.

I still think some standards go too far. I'll probably never get excited about an indentation warning. But I don't think they're pointless anymore either.

Working code matters. It's just not the whole definition of good code.

Good code should work, but it should also be readable and predictable enough that someone else can pick it up without having to reverse-engineer how I think. If putting up with ESLint nagging me about spacing gets me there, I can live with the squiggly lines.

Apparently, making the code work was only step one.
